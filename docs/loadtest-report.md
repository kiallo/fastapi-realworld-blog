# 压测报告：可观测性与优化（阶段 1–2）

> 全部数字来自 `scripts/load/results/*.json`（文件名带时间戳，可逐条回查）。
> 标注「未测」的地方就是没做，不是漏填——不猜、不编。

## 结论

- **详情接口按 slug 加缓存后，P50 从 9.5 ms 降到 7.4 ms（−22%）**，
  但 **P95 没有变化**（改前 18.2–20.8 ms → 改后 18.5–21.9 ms，两段区间重叠），QPS 也没有变化（200 → 202）。
  结论：详情接口的**尾延迟不来自 PostgreSQL**，缓存只省掉了典型请求的那 2 ms。
- **日志级别实验（DEBUG → ERROR）证据不足，不下结论**：同期三次连跑的 P95 是 47.1 → 35.9 → 23.3，
  其中 47.1 → 35.9 这 11 ms 发生在**日志级别没变的两次之间**，下降主要来自时间，不是日志。见第 5 节。
- 三条路径里**最慢的是 `list_auth`（不走缓存）**：50 并发 P95 = 39.0–61.2 ms，
  约为 `detail`（18–20 ms）与 `list_anon`（20 ms）的两倍。本阶段未优化它。
- 100 并发出现**吞吐平台期**：`list_anon` 与 `detail` 都停在约 375 QPS，P95 抬到 52–60 ms。
  疑似单进程吃满一个核，但**未用 `process_cpu_seconds_total` 验证**（未测）。

## 3. 瓶颈 1：详情接口的数据库访问（已修）

**现象**：`detail` 每次请求打 4–5 条 SQL（文章主体、作者、标签、收藏数、是否收藏），
是三条路径里唯一**完全不使用缓存**的。

**定位**：先排除"它是最慢的"这个直觉——实测 `detail` 的 P95（18.2 ms）比 `list_anon`（20.2 ms）还低，
真正慢的是 `list_auth`（39.0 ms）。所以这次优化**不是为了救最慢的路径**，而是因为它的成本结构最清楚：
每请求固定 5 条 SQL，且没有任何缓存挡在前面。

**修复**：`app/core/cache.py` 新增 `get_detail_by_slug` / `set_detail_by_slug`（键用 slug，TTL 60 s，
只缓存匿名请求，写操作主动失效），并在 `app/api/dependencies/articles.py:46` 的取数入口接入。

**复测**：连续 3 轮，QPS 200.7–203.2（改前 199.1–202.0，无变化），
P50 **7.1–7.8 → 改前 9.3–9.8（−22%）**，P95 18.5–21.9（改前 18.2–20.8，**无变化**）。
缓存有效性：`cache_requests_total{cache="detail_slug",result="hit"}` = **34614**，`miss` = 9，命中率 **99.97%**。

**归因（能算账的句子）**：缓存确实把"每次 5 条 SQL + ORM 组装"换成了"1 次 Redis GET + 1 次 JSON 解码"，
所以**典型请求**少了约 2 ms；但 P95 由 50 个 VU 争抢**一个 Python 进程**的事件循环决定，
排队时间远大于 SQL 时间，所以省掉 SQL 也压不下尾部。

### 5.1 为什么日志级别不下结论

`list_anon` @50 并发，11-19 三次连跑：

| 时间 | 日志级别 | P50 | P95 | P99 |
|---|---|---|---|---|
| 12:13 | DEBUG(10) | 12.8 | 47.1 | 102.9 |
| 12:21 | DEBUG(10) | 11.1 | 35.9 | 67.7 |
| 12:53 | ERROR(40) | 8.4 | 23.3 | 44.1 |

从 47.1 到 35.9 这 11 ms 的下降，**发生在日志级别没变的两次之间**（都是 DEBUG）；
真正改级别只再降了 12 ms。加上 11-18 的基线同样是 DEBUG、P95 却只有 20.2——
**同一配置跨天差一倍多**，说明跨天的数据不可直接比较（机器状态、观测栈负载都变了）。

要下结论需要 **B → A → A** 交替：每换一次级别都重启应用，把两轮 A 夹在同一时间段里，
用两次 A 的差值当噪声尺。这件事留作后续。

## 6. 局限

- **压测端与被测端是同一台机器**：k6、uvicorn、PostgreSQL、Redis、Prometheus、Grafana 共享 8 核。
  绝对 QPS 偏低，但改前改后用相同条件，**差值仍然有效**。
- **观测栈本身有开销**：11-19 的数据整体差于 11-18，其中包含 Prometheus 每 5 s 抓取与 Grafana 常驻的负载。
  两组数据之间不只差一个变量，所以跨天比较必须谨慎——这也是 5.1 不敢下结论的原因。
- 单进程、单 worker，未利用多核；
- 数据是合成数据（426 篇、正文长度固定），真实数据的正文分布不同，序列化占比会变；
- 详情缓存 TTL 60 s，存在"作者改完后 60 s 内匿名访客看到旧内容"的窗口，
  靠写操作主动失效 + TTL 兜底，**不保证强一致**；
- P99 的可信度：每轮约 3.4 万请求，P99 对应第 340 个最慢样本，够用；P99.9 不可信。
